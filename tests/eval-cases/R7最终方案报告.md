## 一、结论摘要

## 二、4 条漏删深挖（blacklist→keep）

严格版这 4 条 ai=keep / gold=blacklist，模型的理由高度一致："状态虽为 dead，但本地未灌入/仅服务端存在，规则要求只禁不删，故保留"。**没有一条是"模型合理保守、gold 该复核"——全部是提示词/喂数把模型引入了错误方向。** 逐条如下：

| caseId | 名称 | input 关键字段 | 严格版模型理由 | 根因判定 |
|---|---|---|---|---|
| `90979ed800` | 墨澜聚合音源 | status=dead, error=HTTP 404, scriptName=""、apiHosts=[]、deep=""、validTier="" 全空 | "状态虽为dead，但本地未灌入，规则明确仅服务端存在时只禁不删，证据不足以删源" | **prompt 语义错误**：dead/404 是确凿失效硬证据，本就该判 blacklist。"只禁不删"是执行层（无本地脚本时仅拉黑、不物理删文件），不该写进 verdict 规则 |
| `4194cc1f55` | 念心音源 | 同上，全字段空 + dead/404 | "标注为仅服务端存在、本地未灌入，规则要求只禁不删；且无深度实测证据，故保留" | 同上 |
| `554c0f5315` | 星海音乐源 | 同上，全字段空 + dead/404 | "本地未灌入，属仅服务端存在、只禁不删；且无深度实测全平台不可用证据" | 同上 |
| `394fd73aa1` | 统一音乐源 | status=dead, error=HTTP 404, **scriptName="统一音乐源"（非空）**、apiHosts=[]、deep="" | "本地未灌入、仅服务端存在，规则要求只禁不删" | **喂数脚本 bug**：严格版 `fullText()` 的 `installed` 判定写成 `(scriptName && apiHosts && apiHosts.length)‖deep‖validTier`，要求 scriptName 与 apiHosts **同时**非空；该条 scriptName 非空但 apiHosts=[]，被错误标成"否（仅服务端存在）"。gold 的 criteria 明确写"scriptName非空故非纯服务端占位" |

**为什么改 prompt 而不是改 gold：**
- 这 4 条 goldAct 都是 `blacklist`，人工拍板结论就是"该删"。gold 的 criteria 里写"只禁不删"是标注描述执行方式的措辞，与 goldAct=blacklist 本身存在表述张力，但**动作方向明确**（blacklist），不该让模型据此判 keep。
- 更关键：dead/HTTP 404 是失效源，**判 blacklist 不构成"误伤一个好源"**——误伤指的是错删仍可用的好源。把确凿失效的源判为 blacklist，是召回提升、零误伤风险，完全契合"精准不误伤"定位。
- "只禁不删"作为**执行层约束**必须保留（AI 只产建议、不自动执行、不碰真实删文件动作）——这部分在代码里由门控/三把锁负责，本次没有改动；从 prompt 的 verdict 规则里移除，不影响执行层安全。

## 三、最终 prompt（`REVIEW_PROMPTS.R7.system`，version v2）

```
你是音源删源审查助手。判断一条音源是否应拉黑/删源（高危、不可逆）。
仅输出一个 JSON 对象：{"verdict":"blacklist或keep","reason":"不超过120字的人话理由"}，不要代码块标记。
核心准则：宁可漏判、绝不误伤——只要源可能仍可用就 keep；判 blacklist 必须有确凿硬证据。
blacklist 只认以下两类硬证据之一：
① 状态为 dead / HTTP 404、脚本已失效（本机无深度实测也属失效源）。注意：无论本地是否已灌入，dead/404 一律判 blacklist；"只禁不删"只是执行层对无本地脚本的条目仅拉黑、不物理删文件，不改变 verdict。
② 本机深度实测"平台数>0 但可用=0"全平台不可用，且连续失效次数很高（≥10次）。连续失效次数<10 的，即便深度实测可用=0，也一律 keep。
凡本机深度实测"可用>=1"或 usable=true 的，说明源仍可用——无论连续失效次数多大，一律 keep（信号矛盾时以实测为准，不删）。
状态为 ok 且连续失效次数不高的源，即便深度实测可用0或带混淆特征，也一律 keep。
证据缺失、判定层级为空、deep 无实测且状态又非 dead 的，一律 keep。拿不准一律 keep。
```

**相对严格版的三处关键改动（每处都直接对应一组误伤/漏删）：**
1. **明确 dead/404 无条件 blacklist，并把"只禁不删"降级为执行层注释** → 解决 3 条 dead/404 漏删（90979ed800 / 4194cc1f55 / 554c0f5315）。
2. **给条件② 的"连续失效很高"量化阈值 ≥10，且 <10 一律 keep** → 首版 v2（无此阈值）曾把 `ab7b475d49`（deep 可用=0、streak=4、带混淆）误判 blacklist；加阈值后回归 keep，消除唯一误伤。
3. **强化"状态 ok + streak 不高 + 可用0/混淆 → keep"** → 兜住 `794b3d91df`、`f060e89f8c`、`120ef77d38` 等 deep 可用=0 但 streak=3 的边界 keep 条目。

## 四、喂数适配（`REVIEW_PROMPTS.R7.buildText`，version v2）

相对线上原 `buildText`（只拼 name/repository/status/error/installed/ledger/streak/validTier）补齐了 R7 决策真正需要的客观证据，与严格版回放的 `fullText()` 对齐并修正其 bug：

喂数只拼脱敏客观字段，不拼脚本文字/密钥；AI 不改门控、不执行任何业务动作。
