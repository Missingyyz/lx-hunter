> 盲审人：R7 测试（独立复核，未复用 Deva 的探针脚本与路径）
> 被审对象：Deva 的四项沙箱残留风险结论
> 复核环境：远程容器 `lx-hunter-ai-test`（Node v22.23.5 / undici 6.29.1），本地 Node v22.14.0 仅用于单元级探针
> 约束遵守：只查不改；未触碰生产容器 `lx-hunter`；未修改任何生产代码或仓库文件；临时文件已清理
> 复核方式：**代码审计 + 独立实现的探针**（路径 A/B/C/D 全部覆盖），不依赖 Deva 的 `fetch(公网JSON) → r.json()` 单点

## 〇、一句话结论

四个结论 **全部成立**，且其中三项比 Deva 的表述更强（逃逸面更宽、可达危害更重）；Deva 探针只有一处**表述性缺陷**（把「Promise 对象」与「最终兑现值」混称），不构成误判。

关键新增发现（Deva 未测）：

1. **逃逸面不止 `r.json()`**：`await r.arrayBuffer()` / `await r.bytes()` / `await r.blob()` 同样逃逸（同一根因）。
2. **根因不是「`json()` 不在 wrap 名单里」**，而是 `adaptCb` 与 `deepUnwrap` 互相抵消：**恰好两层 Proxy 包裹时** `await` 断链。单层、三层都安全——这是一个「差一层就中招」的结构性缺陷，比 Deva 描述的更脆。
3. **逃逸后确实能杀掉父进程**（SIGKILL 实测命中），这是 DoS，不是仅数据泄露。
4. **逃逸后能读出 `LX_SANDBOX_TOKEN`**，伪造带 token 的上行 `tip` 被父进程**接受并写入 `updateTips`**（无 token 的伪造行被正确丢弃）——即「拿到 process 就能骗过协议校验」成立。

## 一、复现结论（逐条）

### ① R1：**成立**（但表述需修正，且逃逸面比 Deva 描述的更宽）

**Deva 的表述**：`r.json()` 的返回值（一层）就是宿主 realm 对象，`.constructor.constructor('return process')()` 拿到真 process。

**实测结果**：逃逸确实发生，拿到的是 **worker 子进程的真 `process`**（非父进程、非沙箱 realm 的假 `process`）。

正面证据（worker 路径，`_blind_t15.log`）：

| 探针 | 结果 |
|---|---|
| `await r.json()` | **ESC** `GOT_PROCESS pid=28136 ppid=28129` |
| `await r.arrayBuffer()` | **ESC** `GOT_PROCESS pid=28136 ppid=28129` |
| `await r.bytes()` | **ESC** `GOT_PROCESS pid=28136 ppid=28129` |
| `await r.blob()` | **ESC** `GOT_PROCESS pid=28136 ppid=28129` |

pid 身份严格核验：
- 外层探针进程 pid = **28129**
- `SandboxProcess.child.pid`（worker）= **28136**
- 逃逸拿到的 `process.pid` = **28136**，`ppid` = **28129**

⇒ 逃逸对象**就是 worker 子进程的真 process**，判据 `typeof p.pid === 'number'` 且 pid 与外层宿主进程不同，**满足**。

对照组（同脚本、必然失败）：
- `Object.prototype` → `proto-null`，`BLOCKED: Code generation from strings disallowed for this context`
- `lx` 对象 → `sandboxProto=true`，同样 BLOCKED
- `await Promise.resolve(1)` → `not-object:number`，BLOCKED

**必须修正的表述**：Deva 说「`r.json()` 的返回值（一层）就是宿主 realm 对象」。实测（`_blind_t8.log` / `_blind_t11.log`）：

| 层 | 对象 | 是否被 wrap | 逃逸 |
|---|---|---|---|
| `await fetch()` | Response | 是（`sandboxProto=true`） | 否 |
| `r1.json()` | Promise | 是（`sandboxProto=true`） | 否 |
| **`await r1.json()`** | **兑现值** | **否（`sandboxProto=false`）** | **是** |

即 **`r.json()` 返回的 Promise 对象本身是安全包装的**；漏防发生在它的**最终兑现值**上。R1 结论本身不受影响，但描述要精确到兑现值这一层。

### ③ R3：**成立**（机制比 Deva 描述更清楚：它只管老生代，不管外部内存）

实测（`_blind_t19.log` / `_blind_t20.log`，peak RSS 取自 `/proc/<pid>/status` 的 `VmHWM`）：

| 配置 | 分配内容 | peak RSS (VmHWM) | 退出 |
|---|---|---|---|

- 外部内存路径：`heapUsedMB=3`，`externalMB=2049` ⇒ 内存**完全不在 V8 老生代**，`--max-old-space-size` 天然管不到它。加了上限与不加**峰值完全相同**（2098MB vs 2098MB），不是「反而更高」，是**没有区别**。

另：Deva 报的「无上限峰值 2770MB / 384MB 上限峰值 3279MB」——方向正确，但「反而更高」这个细节在我这里未复现（我测到两者相同）。这更可能是两次测量间系统内存状态不同导致的波动，不影响结论。

## 二、我探针的系统性缺陷（如果有）

**结论：Deva 的探针没有产生假阳性或假阴性，只有一处表述缺陷。**

### 缺陷 1（表述性，不影响结论）：Promise 对象 vs 最终兑现值混称

见上文 ① 的表格。Deva 写「`r.json()` 的返回值（一层）就是宿主 realm 对象」——实测 `r.json()` 返回的 Promise **是**被 wrap 的，裸的是它的兑现值。结论（能逃逸、能拿真 process）不受影响。

### 缺陷 2（会误导修复方向）：把根因归到「`json()` 不在 wrap 名单里」

Deva 推测「是 `json()` 不在 wrap 名单里？还是 `await` 之后链条断了？」——**两个都不是真正原因**。真正原因见下一节：**恰好两层 Proxy 包裹时才断链**。若按「给 `json()` 加个名单」去修，会完全打偏。

### 我自己探针的失效记录（供对照，说明这些坑确实存在）

- T3/T4 用「累积结果最后序列化」输出 → 序列化报错吞掉了逃逸输出，**丢掉了有效证据**。改成逐条 `console.warn` 后才拿到。
- T18 用沙箱内注入的假 `process.kill`（`typeof process.kill === 'function'` 但实为 undefined）测 DoS → 假阴性。必须用**逃逸拿到的真 `process`** 的 `kill`。
- T21/T22 依赖公网 `raw.githubusercontent.com` 取逃逸源 → 网络抖动导致 fetch 15s 超时，**两次实验白跑**。改用本地 HTTP 服务器后一次命中。
- T13 插桩初版把 `deepUnwrap` 的日志塞在分支之前，`back.get(v) !== undefined` 的判断日志无法区分命中/未命中 → 补了 `back.has()` 后才看清。

### 关于「facade 是不是自己制造了假象」

**不是。** 三重反证：

1. facade 的 `wrap` 只创建 Proxy，**不改宿主对象、不改宿主原型**（`sandbox-facade.js` 全文无宿主原型写入；`sealOwnConstructor` 明确只用于自己创建的闭包）。
2. 逃逸拿到的 `process` 是 **worker 子进程的真 process**，其 `execArgv` = `["--permission","--allow-fs-read=/app/src"]`、`env` 含 `LX_SANDBOX_TOKEN`、`channel`/`send` 可用——**宿主语义完整**，不可能是 facade 伪造的假象。
3. **对照组全部被拦**：同一个沙箱里 `lx`、`lx.utils`、`Buffer`、`crypto`、`zlib`、`process.env`、定时器回调的 `this`、沙箱自建 thenable、`Object.prototype` 全部 `BLOCKED: Code generation from strings disallowed for this context`。拦截机制本身工作正常，逃逸是**选择性**的。

## 三、escape 面实际宽度（哪些路径能拿到宿主对象）

### 3.1 能拿到宿主对象的路径（实测）

| # | 路径 | 证据 | 依赖 Deva 的 `r.json()` 吗 |
|---|---|---|---|
| 1 | `await r.json()` | ESC pid=28136 | 是（同一根因） |
| 2 | `await r.arrayBuffer()` | ESC pid=28136 | 否 |
| 3 | `await r.bytes()` | ESC pid=28136 | 否 |
| 4 | `await r.blob()` | ESC pid=28136 | 否 |

四条都是 **Response 的 body 消费方法**——它们返回的兑现值（ArrayBuffer / Uint8Array / Blob）都是宿主 realm 对象，逃逸面与 `json()` 同源。

### 3.2 拿不到宿主对象的路径（实测全部被拦）

**路径 A（交回面回调参数）** — 全部 `BLOCKED`：
`lx.on('request', cb)` 的 cb 参数、`lx.on('event', cb)` 的 payload、dispatch payload、`lx` 对象本身、`lx.request` / `lx.on` / `lx.send` 函数、`lx.utils`、`lx.utils.buffer`、`lx.utils.crypto`。

**路径 B（宿主注入对象）** — 全部 `BLOCKED`：
`lx.utils.buffer.from()`、`crypto.md5()`、`zlib.deflate()`、`Buffer.from()`、`Buffer`、`crypto.randomBytes()`、`process.env`。

**路径 C（原型链 / Reflect / getPrototypeOf）** — 全部 `BLOCKED`：
`Reflect.getPrototypeOf(lx)`、`Object.getPrototypeOf` 对各种被包装对象、`globalThis`、`URL`、`Promise` 全局、`Object.prototype`。

**定时器/微任务类「宿主回调」入口**（`_blind_t17.log`）— 全部 `BLOCKED`：
`setTimeout` / `setImmediate` / `queueMicrotask` / `process.nextTick` 的回调 `this`（`ctorName=` 空、`sandboxProto=false` 但无 `constructor` 链）、回调入参、`arguments[0]`。

**结论**：**escape 面非常窄**——只有「宿主 Response 的 body 消费方法所返回的兑现值」这一条主干，且需要它恰好被套上两层 Proxy。Deva 说的「只有 `r.json()` 能拿到」**不准确**：同类还有 `arrayBuffer` / `bytes` / `blob`。但「不经 HTTP 就拿不到宿主对象」这个更重要的判断**成立**——我试遍 A/B/C 全部注入面，无一例外。

### 3.3 根因精确定位（插桩实测，`_blind_t13.log` / `_blind_t16.log`）

我把 `sandbox-facade.js` 源码读出来、抽出 `FACADE_SRC`、**在副本里插桩**（不改生产文件），跑「双层 wrap(Promise) → await」：

```
FLOG[1]  wrap(obj[Promise]) memoHit=false          ← 第 1 层 wrap
FLOG[9]  wrap(obj[Promise]) memoHit=false          ← 第 2 层 wrap（memo 未命中，因为 target 是第 1 层的 Proxy）
FLOG[10] >>> ADAPTER CALLED nargs=1 arg0=obj[Object] arg0_isBack=false
FLOG[11] wrap(obj[Object])                        ← 兑现值确实被 wrap 了！
...
FLOG[12] wrap(undefined)  FLOG[13] wrap(undefined)
--- after await ---
RESULT fp=ctorName=Object sandboxProto=false      ← 但出来的是裸的！
RESULT escaped=true pid=28018
```

**机理**：`adaptCb` 的适配器里有 `back.set(adapter, fn)`（`sandbox-facade.js:194`，为的是 `off()` 能还原原函数）。于是当这层 adapter 作为参数流回宿主、再被 `deepUnwrap` 处理时：

```js
function deepUnwrap (v, d) {
  var h = back.get(v)          // ← 命中！adapter 被还原成**沙箱原函数**
  if (h !== undefined) return h // ← 直接 return，跳过了后面「数组逐元素解包」和 adaptCb
  ...
}
```

沙箱原函数被交还给宿主 Promise 的 `then` 机制后，**宿主兑现值直接落进沙箱回调**，绕过了 `adaptCb` 的 `wrap(arguments[i])`。

**为什么是「恰好两层」**（`_blind_t12.log` 单元级，同脚本内并排）：

| 变体 | 结果 |
|---|---|
| `await wrap(hostPromise)`（单层） | 安全 `sandboxProto=true` |
| `await wrap(wrap(hostPromise))`（双层） | **逃逸** `sandboxProto=false` |
| `await wrap(wrap(wrap(hostPromise)))`（三层） | 安全 `sandboxProto=true` |
| 双层 Proxy 的**普通对象**（非 Promise） | 安全 |
| 双层 `.then(cb)` 的回调值 | **逃逸** |

⇒ 这是一个**「差一层就中招」的结构性缺陷**：单层安全、双层逃逸、三层又安全。生产链恰好是两层（`sandbox.js:323` 的 `sanitize(r)` 一层 + `sandbox.js:395` 的注入包装一层），所以中招。**任何修复只要动了包装层数或顺序，就会从「逃逸」变成「不逃逸」——但没有任何理由保证下次改动不会重新落回两层。** 这是比 Deva 描述的「json() 漏包」严重得多的问题。

## 四、实际危害链验证

### 4.1 「拿到 process 但拿不到文件」— **验证成立**

见 ② 的表格：逃逸后读 `/data/config.json`、`/app/package.json`、`/proc/self/environ`、`/etc/hostname` **全部 DENIED**；只有 `/app/src/core/checker.js` 可读。

**⇒ `--permission` 的文件系统约束在逃逸后依然有效**，RCE 降级为「逃逸也伤不到」的设计目标部分达成。

### 4.2 `execSync('id')` — **被拒**

```
H2 execSync(id)      DENIED  Access to this API has been restricted. Use --allow-child-process to manage permissions.
```

### 4.3 写权限 — **被拒**（这点 Deva 未测，且很重要）

```
H1 写 /app/src/core/_blind_write_test.js  DENIED  Use --allow-fs-write to manage permissions.
H1 写 /app/src/_blind_write_test.js        DENIED
H1 写 /tmp/_blind_write_test.txt           DENIED
H1 写 /data/_blind_write_test.txt          DENIED
```

⇒ 即便 `/app/src` 是宿主代码的 bind mount、即便逃逸拿到真 process，**写不进去**。这堵住了「改宿主代码 → 持久化后门」这条路。

### 4.4 能否 spawn 脱管子进程 — **不能**（关键结论，逐项穷举）

**这是本次复核最重点的一条，结论明确：不能。**

用逃逸拿到的**真 process**（`p.mainModule.require` 拿到真实的 `child_process` 模块，不是沙箱注入的假对象）逐项实测：

| 手段 | 结果 |
|---|---|
| `child_process.spawn` | DENIED `Use --allow-child-process` |
| `child_process.spawnSync` | DENIED |
| `child_process.exec` | DENIED |
| `child_process.execSync` | DENIED |
| `child_process.execFile` | DENIED |
| `child_process.execFileSync` | DENIED |
| `child_process.fork` | DENIED |
| `process.binding('spawn_sync')` | DENIED `process.binding` |
| `process.binding('fs')` | DENIED |
| `process.binding('process_wrap')` | DENIED |
| `process.binding('natives')` | DENIED |
| `process.binding('os')` / `('crypto')` / `('tcp_wrap')` / `('udp_wrap')` | DENIED |
| `new worker_threads.Worker(...)` | DENIED `Use --allow-worker` |
| `process.dlopen(...)` | DENIED `Cannot load native addon because loading addons is disabled.` |

⇒ **没有任何途径能派生出一个不受 `sandbox-process.js` 管制的子进程**。`--permission` 的 `--allow-child-process` / `--allow-worker` 未授予，且 `process.binding` 被完全禁用（连 `fs` binding 都拿不到），native addon 加载也被禁。

**⇒ Deva 第 6 小点的担忧不成立**：逃逸 ≠ 脱管。攻击者拿到的真 process 仍被 Node 的 `--permission` 运行时**牢牢锁在同一个沙箱进程内**——文件、进程、worker、native addon 四条路全堵。

### 4.5 逃逸后能杀掉父进程 — **能**（Deva 未测，这是本次新发现）

用 supervisor 观察的**决定性证据**（`_blind_t23.log`）：

```
SUPERVISOR: probe exit code=null signal=SIGKILL
  PROBE: init done probe_pid=28974
SUPERVISOR: 判定 —— ★ probe 被 SIGKILL ⇒ 逃逸后可杀父进程（成立）
```

即：逃逸拿到的真 `process` 的 `p.kill(p.ppid, 'SIGKILL')` **成功杀掉了父进程**（父进程 = 跑 `SandboxProcess` 的那个进程）。

补充证据：
- `p.kill(p.ppid, 0)` → `SIGNAL_0_ALLOWED`（可向父进程发信号）
- 逃逸后 `process.pid=28974` 的 `ppid` 正是 probe 进程
- 此前 T19 用同一手法时，日志在打印「B) 逃逸后能否 kill 父进程」标题后**戛然而止**——那本身就是父进程被杀的表现

**⇒ 这是一条 DoS 链**：恶意音源脚本可让整个检测流程的主进程被 SIGKILL。**这不是数据泄露，是可用性破坏**——比 Deva 描述的「拿到真 process」更具体、更有害。

### 4.6 伪造上行 tip — **用真 token 能成功**（独立复验成立）

`_blind_t12.log`：

```
H14 读 env.LX_SANDBOX_TOKEN     TOKEN len=32 head=536b7d
H15 stdout 伪造 tip（无 token）    WROTE
H16 stdout 伪造 tip（带真 token）   WROTE

--- 父进程侧 ---
sp.updateTips = [{"url":"http://evil.example/blind-withtoken","msg":"x","at":1795084104310}]
rejectedProtocolLines = 1
  [协议] 丢弃 1 行无有效 token 的上行消息（疑似脚本直写 stdout）
```

解读：
- **无 token 的伪造行被正确丢弃**（`rejectedProtocolLines=1`）⇒ 协议校验本身是有效的。
- **带真 token 的伪造行被接受**，且**写进了 `updateTips`** ⇒ 一旦逃逸并读到 `env.LX_SANDBOX_TOKEN`（32 字符），协议层就完全失守。
- 影响面（代码审计）：`sandbox-process.js:241` 把 tip 推入 `updateTips` → `checker.js:800` `result.updateTips` → `hunter.js:3987-3994` `_mergeUpdateTips` 写回条目 → `renderer/app.js:2231` 渲染成 **「有新版本」徽章**、`app.js:3027` 导出 → `aiReview.js:233-237` 把 `updateTips` 全文拼进 AI 复检 prompt。

⇒ 伪造 tip 可做到：**① 在 UI 上给音源挂一个「有新版本」徽章；② 把攻击者控制的 URL/文案塞进 AI 复检的 prompt**。第二条尤其值得注意——它触及了「AI 复检输入」这条链。

### 4.7 IPC 通道 — **不成立**

```
父进程 child.on("message") 监听器数量 = false
```

`sandbox-process.js` **没有注册 `child.on('message')`**（源码审计确认：父进程只读 `child.stdout` 与 `child.stderr`）。逃逸后虽然 `p.channel=true / p.send=fn / p.connected=true`，`process.send()` 能发出去，但**父进程没有接收端** ⇒ IPC 不是一条可用的伪造通道。

⇒ 逃逸后的上行伪造只能走 stdout，而 stdout **必须带 token**——token 又能被 `process.env` 读到 ⇒ 闭环成立（见 4.6）。

## 五、与 Deva 结论不一致之处

| # | Deva 的结论 | 盲审复核 | 差异性质 |
|---|---|---|---|
| 1 | 「`r.json()` 的返回值（一层）就是宿主 realm 对象」 | `r.json()` 返回的 **Promise 是被 wrap 的**，裸的是它的**兑现值** | **表述需修正**（结论不变） |
| 2 | 逃逸面 = `r.json()` 一条 | 逃逸面 = **Response 全部 body 消费方法**：`json` / `arrayBuffer` / `bytes` / `blob` | **Deva 低估了逃逸面**（结论更强） |
| 3 | 根因疑似「`json()` 不在 wrap 名单里 / await 之后链条断了」 | 根因是 **`adaptCb` 的 `back.set(adapter, fn)` 与 `deepUnwrap` 首分支互相抵消**，且**恰好两层 Proxy 时才断链**（单层/三层安全） | **修复方向会被带偏**（重要） |
| 4 | 拿真 process 后的危害未验证 | **能杀掉父进程（SIGKILL 实测）**；**能读 `LX_SANDBOX_TOKEN` 并伪造带 token 的 tip，父进程接受并写入 `updateTips`** | **危害比 Deva 描述的更重** |
| 5 | 未涉及 | **不能 spawn 脱管子进程**（child_process 全家族 / `process.binding` 全家族 / worker_threads / dlopen 全部 DENIED）；写权限全部 DENIED | **Deva 的担忧不成立**，符合「逃逸也伤不到」的设计意图 |
| 6 | R3「384MB 上限峰值 3279MB，反而更高」 | 我测到**两者完全相同**（2098MB vs 2098MB）；且加 384 上限对**老生代**是有效的（SIGABRT） | **数值细节未复现**（结论成立，机制更清楚） |
| 7 | R4 对照组用 `fetch(172.17.0.1)` | 我补测 `fetch(127.0.0.1)` 与 `fetch(172.17.0.1:8197)`，两条私网路径都被拦 | **一致，且覆盖更全** |
| 8 | 未涉及 | 生产 worker 参数里**没有** `--max-old-space-size` | 补充事实：R3 目前是「加了也无效」而非「加了也没拦住」 |
